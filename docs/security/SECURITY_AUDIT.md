# Auditoría de seguridad

Fecha: 23 de julio de 2026.

## 1. Alcance y método

Revisión estática de frontend, backend, configuración, lockfiles, Docker, Git, historial accesible,
PWA, IndexedDB, endpoints, tests y documentación. Se ejecutaron comprobaciones npm y búsquedas
redactadas de secretos. No se atacó ningún sistema externo ni se usaron datos reales.

Estados:

- **Implementado, pendiente de prueba:** existe en código, pero la suite final/CI aún debe pasar.
- **Verificado estáticamente:** comprobado por lectura o herramienta local de solo lectura.
- **Pendiente de infraestructura:** necesita dominio, proveedor o credenciales.
- **Abierto:** no resuelto.
- **N/A:** no aplica a la arquitectura actual.

No se afirma que MIGA sea “segura”, conforme al RGPD ni ASVS L2. La checklist detallada está en
[OWASP_ASVS_CHECKLIST.md](OWASP_ASVS_CHECKLIST.md).

## 2. Arquitectura detectada

- React 19/TypeScript/Vite PWA.
- ASP.NET Core/.NET 10, Identity, cookies y antiforgery.
- EF Core/Npgsql/PostgreSQL con esquemas `auth`, `app` y `audit`.
- Workspaces demo/registrado y snapshots JSON.
- IndexedDB aislado por identidad.
- Blobs de PDF/vídeo/audio/imagen exclusivamente locales.
- SMTP opcional, YouTube Data API/IFrame API y Data Protection persistido en PostgreSQL.
- GitHub Actions, Dependabot, npm/NuGet lockfiles y PostgreSQL fijado por digest.

## 4. Secretos e historial

La revisión inicial por patrones abarcó 241 archivos de texto y los diffs accesibles de 62 commits.
Después, Gitleaks `8.30.1`, descargado desde su release oficial y verificado con SHA-256, ejecutó:

- `gitleaks dir`: aproximadamente 7,47 MB del árbol actual, cero filtraciones detectadas;
- `gitleaks git`: 62 commits y aproximadamente 1,48 MB, cero filtraciones detectadas.

La revisión manual complementaria:

- no encontró patrones fuertes de clave privada, PAT GitHub, AWS, Google, Slack, Stripe o JWT
  completos;
- sí confirmó una antigua contraseña PostgreSQL de desarrollo repetida en configuración/documentos;
- el valor fue eliminado del árbol actual y sustituido por un marcador en las bitácoras;
- no se reescribió Git.

El valor histórico tenía entropía baja y Gitleaks no lo clasificó como secreto; por eso el resultado
automático no elimina la obligación de rotarlo si se reutilizó. El mismo escaneo está configurado en
CI, pero el workflow aún no se ha ejecutado. No se inspeccionaron objetos Git
inaccesibles/dangling, forks ni cachés externos.

## 5. Dependencias

Resultado observado sobre los lockfiles finales:

```text
root, auditoría completa:       0 vulnerabilidades (exit 0)
frontend, auditoría completa:   0 vulnerabilidades (exit 0)
root, --omit=dev:               0 vulnerabilidades (exit 0)
frontend, --omit=dev:           0 vulnerabilidades (exit 0)
```

`concurrently`, que no se usaba, fue retirado del manifiesto raíz y el lockfile frontend resolvió
versiones corregidas de sus transitivas. Este resultado es puntual a la fecha de la auditoría y no
sustituye Dependabot ni la comprobación recurrente en CI.

Los lockfiles npm v3 tienen integridades y no resuelven dependencias desde Git. Los proyectos .NET
usan lockfiles. La auditoría NuGet final recorrió los siete proyectos y no informó paquetes
vulnerables; el control se repite en CI.

El job de imagen no ejecuta `trivy-action` ni `setup-trivy`: descarga el binario oficial `0.72.0`,
comprueba el SHA-256 publicado y escanea la referencia PostgreSQL por digest. Esta decisión reduce
la superficie tras el
[incidente oficial del ecosistema Trivy de marzo de 2026](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23);
la versión y su checksum requieren mantenimiento deliberado.

## 7. Verificación pendiente antes de producción

1. workflow GitHub completo verde y checks requeridos en `main`;
2. tests cruzados de autorización/demo y todos los flujos de auth;
3. escaneo de imagen sin Critical/High no aceptados;
4. migración PostgreSQL limpia/doble, desde versión anterior y script idempotente revisado;
5. dominio HTTPS real, headers, CORS, hosts y proxy;
6. SMTP sandbox y producción, sin tokens en logs;
7. persistencia/rotación/restauración del keyring;
8. backup PostgreSQL restaurado en entorno aislado;
9. pruebas multiinstancia o rate limiter/cache distribuidos;
10. revisión jurídica y política de retención;
11. decisión explícita para los blobs local-only.

Hasta completar esos puntos, MIGA no está preparada para producción.
